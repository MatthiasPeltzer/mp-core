# Configuration

Site Sets, Site Settings, TypoScript, and TCA configuration reference.

---

## Site Sets (TYPO3 13.4+)

| Set | Purpose |
|-----|---------|
| `mpc/mp-core` (aggregator) | Pulls in all feature sets below in one include |
| `mpc/mp-core-base` (required) | Core functionality, templates, base styling, shared settings |
| `mpc/mp-core-container` | Container elements (accordion, tabs, slider, grid) |
| `mpc/mp-core-news` | News extension integration |
| `mpc/mp-core-form` | Form framework configuration |
| `mpc/mp-core-seo` | SEO (Open Graph, Twitter Cards, Schema.org, sitemap) |

`mpc/mp-core` is an aggregator that depends on `mpc/mp-core-base` plus all feature sets. Including only `mpc/mp-core` in your site is sufficient. If you need fine-grained control, include `mpc/mp-core-base` and pick individual feature sets.

### Set roles

| Set | Role |
|-----|------|
| `mpc/mp-core` | Aggregator + shared Site Settings (`settings.yaml`, `settings.definitions.yaml` in this folder) |
| `mpc/mp-core-base` | Pulls in TYPO3 system extensions; registers the shared settings paths above; optional integrations when present |
| `mpc/mp-core-*` (feature) | Feature-specific TypoScript and settings; each depends on `mpc/mp-core-base` only |

> **Important:** When authoring a custom Site Set, set `dependencies: [mpc/mp-core-base, …]` — never `mpc/mp-core`. Depending on the aggregator from a child set causes a SetRegistry recursion deadlock.

### `mpc/mp-core-base` dependencies

Required: `typo3/form`, `typo3/redirects`, `typo3/indexed-search`

Optional (used when installed): `georgringer/news-recordlinks`, `georgringer/news-sitemap`, `mpc/mpc-vidply`, `mpc/mpc-rss`

### Enabling Sets

**Backend:** Site Management -> Sites -> Sets tab -> enable and order sets.

**YAML** (`config/sites/[site]/config.yaml`):

```yaml
base: 'https://example.com'
rootPageId: 1
dependencies:
  - mpc/mp-core
```

Or cherry-pick individual sets:

```yaml
dependencies:
  - mpc/mp-core-base
  - mpc/mp-core-container
  - mpc/mp-core-seo
```

### Using Settings in TypoScript

Site settings are exposed as flat TypoScript constants under their dotted key (no `settings.` prefix), e.g. `{$navigation.maxDepth}`, `{$config.admPanel}`, `{$PIDs.pidWebFonts}`. The path settings (`pageTemplates`, `basePath`, …) are additionally exposed with a `settings.` prefix, which is why the `mpcSitepackage.*` path constants reference `{$settings.pageTemplates}`.

For values that must be resolved at render time (e.g. inside `config`, `page.meta`, or DataProcessor properties), read them directly via the `site:settings.*` data getter instead of a constant:

```typoscript
# Flat constant (resolved at TypoScript parse time)
page.10.dataProcessing.110.levels = {$navigation.maxDepth}

# Runtime getter (preferred for config / meta / processor stdWrap)
config.compressJs.data = site:settings.performance.compressJs // {$config.compressJs}
page.meta.robots.data = site:settings.meta.robots
```

Font design tokens are not consumed via TypoScript: they are generated from the Web Font records (see [Web Fonts](#web-fonts)) by `WebFontProcessor` and emitted as CSS custom properties in `Resources/Private/Partials/Page/Styles.html`.

## Web Fonts

Editors can self-host custom fonts (uploaded to / picked from the FileManager) instead of relying on system fonts. The feature replaces the former `design.fonts.*` string settings.

### Data model

| Record | Table | Purpose |
|--------|-------|---------|
| Web Font Family | `tx_mpcore_domain_model_webfontfamily` | One CSS `font-family` (name + fallback stack), assigned to a target CSS variable |
| Font Face | `tx_mpcore_domain_model_webfontface` | One uploaded font file per weight/style (inline child of a family) |

A family's **Applies to** field maps it to a CSS custom property:

| Role | CSS variable |
|------|--------------|
| Body text | `--bs-body-font-family` |
| Headings | `--bs-font-sans-serif` |
| Custom CSS variable | the `--…` name entered in the family record |

### Editor workflow

1. Create a sysfolder to hold the records and set its page ID in the `PIDs.pidWebFonts` site setting. Leave it at `0` to store the records on the site root page.
2. In the List module of that folder, create a **Web Font Family**: enter the family `name` (e.g. `Inter`), a `fallback` stack (e.g. `sans-serif`), and choose **Applies to**.
3. Add one **Font Face** per weight/style. Upload or pick a `woff2` file via the FileManager and set its weight (100–900) and style (normal/italic).
4. Flush the frontend cache. `WebFontProcessor` generates the `@font-face` rules and the `:root` variable mapping into the nonce'd inline `<style>` block in the page `<head>`.

### Rendering pipeline

```
Webfont records (FAL files)
  -> WebFontProcessor (page.headerData.2040.dataProcessing.20)
  -> WebFontCssBuilder (validate + sanitize, build @font-face + :root CSS)
  -> {webFontsCss} in Styles.html
  -> <f:asset.css useNonce="1"> + mpc:format.cssSanitize
```

All values are validated against fixed allow-lists in `WebFontCssBuilder` (weight, style, `font-display`, file format, custom-variable name, `unicode-range`) and the family name / fallback / URL are stripped of any character that could break out of the CSS declaration, so an attacker-supplied value can never escape the inline `<style>` block.

### Constraints

- **CSP:** self-hosted fonts in `fileadmin` are same-origin and already covered by `font-src 'self'` in `Configuration/ContentSecurityPolicies.php`. Serving fonts from another domain requires adding that origin to `font-src` via a per-site `config/sites/<id>/csp.yaml`.
- **Backend permissions:** admins can edit the records immediately. Non-admin backend groups need `tables_modify` (and `tables_select`) granted for `tx_mpcore_domain_model_webfontfamily` and `tx_mpcore_domain_model_webfontface`.
- A family is only emitted when it has at least one face with a resolvable font file; otherwise the `:root` mapping is skipped (the family name alone would not load anything).

## Site configuration (`config.yaml`)

Beyond Site Settings, mp-core extends the **site record** and **site language** via `Configuration/SiteConfiguration/Overrides/sites.php`. Configure these in **Site Management → Sites → [site] → Configuration** (or in `config/sites/[site]/config.yaml`).

| Area | Fields (examples) | Notes |
|------|-------------------|-------|
| Customization | `navType`, `subnav`, `subnavOrder`, `search`, `copyrightText` | `navType`: `1` primary, `2` secondary, `3` tertiary |
| Favicons | `favicon-96x96-png`, `faviconIco`, `faviconSvg`, `apple-touch-icon`, `webmanifest`, … | File links → `Resources/Private/Partials/Page/Favicons.html` ([Favicons.md](Favicons.md)) |
| Colors & styles | `color-toggle`, `color-1`…`color-8`, `color-primary`, `styles` | `styles` injects custom `:root` CSS; pairs with `ColorPickerValueItems` in TCA |
| Social media | `socialMediaSwitch`, platform URL fields | Fed into `SocialMediaProcessor` / structured data |
| Logos | `logoBig`, `logoSmall`, `logoSvg`, `logoText`, `logoTextHidden` | Per-language overrides on site languages; resolved by `HeaderLogoProcessor` |
| Structured data entity | `extraEntityImage` | FAL file link for optional Schema.org extra entity (`StructuredDataProcessor`); type/name/keywords in Site Settings |

Language-specific palettes: `copyrightText`, logo fields, and `logoText` / `logoTextHidden` can differ per site language.

#### Local-only DI overrides (`Services.local.yaml`)

The shipped `Services.yaml` imports an optional sibling file with `ignore_errors: not_found`, so projects can register local-only services (tooling commands, ad-hoc helpers) without modifying the published file or breaking container compilation when the file is absent:

```yaml
# Configuration/Services.local.yaml  (gitignored)
services:
  Mpc\MpCore\Command\ImportDocumentationCommand:
    tags:
      - { name: console.command, command: 'docsite:import' }
```

`Configuration/Services.local.yaml` is listed in `.gitignore` for this exact pattern.

### Content Security Policy (`ContentSecurityPolicies.php`)

`Configuration/ContentSecurityPolicies.php` ships a strict frontend CSP that is
auto-applied by TYPO3 13.4+ once one of these feature toggles is enabled
(**System -> Settings -> Feature Toggles**):

- `security.frontend.enforceContentSecurityPolicy` -- enforce mode
- `security.frontend.reportContentSecurityPolicy` -- report-only mode

The shipped policy mutates the TYPO3 frontend defaults as follows:

| Directive | Mutation | Rationale |
|-----------|----------|-----------|
| `default-src` | `Set 'self'` | Strict baseline; everything without its own directive must be same-origin. |
| `script-src` | `Extend nonceProxy` | Inline `<script>` blocks (`ThemeInit.html`, JSON-LD `<script type="application/ld+json">`) are nonce-gated via `<f:security.nonce()>`. |
| `style-src` | `Extend nonceProxy` | Inline `<style>` blocks (colour overrides in `Styles.html`, per-element background image in `fluid_styled_content/Layouts/Container.html`) use `<f:asset.css useNonce="1">`. |
| `img-src` | `Extend data:` | Allow SCSS-emitted inline SVG fallbacks (`svg-load`) and base64 placeholders. |
| `font-src` | `Set 'self'` | All webfonts are self-hosted in `Resources/Public/Fonts/`. |
| `connect-src` | `Set 'self'` | No XHR/fetch/WebSocket beyond own origin. |
| `object-src` | `Set 'none'` | Block legacy plugins (`<object>`, `<embed>`, `<applet>`). |
| `base-uri` | `Set 'self'` | Prevent `<base href>` injection attacks. |
| `form-action` | `Set 'self'` | Forms post back to same origin only. |
| `frame-ancestors` | `Set 'self'` | Clickjacking defence: not embeddable cross-origin. |

#### Per-site overrides

Operators can relax or tighten the policy per site via
`config/sites/<id>/csp.yaml`:

```yaml
inheritDefault: true
mutations:
  - mode: extend
    directive: img-src
    sources: ["https://cdn.example.com"]
  - mode: extend
    directive: form-action
    sources: ["https://newsletter.example.com"]
```

#### Trust boundary for site colour configuration

Inline CSS variables in `Resources/Private/Partials/Page/Styles.html` are now
funnelled through the `mpc:format.cssColor` ViewHelper, which delegates to
`Mpc\MpCore\Service\CssColorValidator`. Only syntactically valid CSS colours
(named, `#rgb[a]`, `#rrggbb[aa]`, `rgb()/rgba()/hsl()/hsla()`) are emitted;
malformed or attacker-supplied site-configuration entries are silently
dropped, so they can never break out of the inline `<style>` block.

The same validator is reused in `Mpc\MpCore\UserFunc\ColorPickerValueItems`
so the backend colour-picker dropdown also filters out invalid slots and
caps labels at 200 characters.

```typoscript
    10 = {$settings.pagePartials}
  }
  layoutRootPaths {
    0 = EXT:mp_core/Resources/Private/Layouts/
    10 = {$settings.pageLayouts}
  }
}
```

Path precedence: `0` = core, `10` = extension, `20+` = project. Higher numbers override lower.

### Extension Overrides

```typoscript
plugin.tx_news.view.templateRootPaths.10 = EXT:mp_core/Resources/Extensions/news/Templates/
plugin.tx_form.view.templateRootPaths.10 = EXT:mp_core/Resources/Extensions/form/Templates/
plugin.tx_indexedsearch.view.templateRootPaths.10 = EXT:mp_core/Resources/Extensions/indexed_search/Templates/
```

### Conditional Configuration

Navigation bundles depend on the site configuration field `navType` (see `Configuration/SiteConfiguration/Overrides/sites.php`):

| `navType` | Layout |
|-----------|--------|
| `1` | Primary navigation |
| `2` | Secondary navigation |
| `3` | Tertiary navigation |

```typoscript
[traverse(site("configuration"), "navType") == "1"]
  page.includeJSFooter.navigationPrimary = EXT:mp_core/Resources/Public/JavaScripts/navigationPrimary.js
[END]
```

## Common Customization Patterns

### Adding a Field to an Existing Element

```php
$myColumns = [
    'tx_my_field' => [
        'label' => 'My Field',
        'config' => ['type' => 'input', 'size' => 30],
    ],
];
ExtensionManagementUtility::addTCAcolumns('tt_content', $myColumns);
ExtensionManagementUtility::addToAllTCAtypes('tt_content', 'tx_my_field', 'textmedia', 'after:bodytext');
```

### Database Schema

Add columns to `ext_tables.sql`, then run **Admin Tools -> Maintenance -> Analyze Database Structure**.

```sql
CREATE TABLE tt_content (
    tx_my_field varchar(255) DEFAULT '' NOT NULL
);
```

## Tips

1. **Reuse existing palettes** from `tt_content_00_base.php` and `tt_content_00_header.php`
2. **Prefix custom fields** with `tx_` to avoid conflicts
3. **Use `LLL:EXT:...`** references for all labels
4. **Use `displayCond`** for conditional field visibility: `'displayCond' => 'FIELD:my_toggle:=:1'`
5. **Use Site Settings** instead of hardcoded TypoScript values
6. **Follow path numbering**: `0` (core), `10` (extension), `20+` (project)
